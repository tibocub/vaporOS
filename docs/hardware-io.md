# Hardware I/O: what NuttX gives us (survey, 2026-10-27)

Read from the NuttX tree next to this repo (releases/13.0 era). Nothing here was run on a board: the RP2040 is
unplugged. Facts below are from source; the **gaps** are what vaporOS has to add.

## GPIO

- **Userspace interface:** `/dev/gpioN` character devices (`CONFIG_DEV_GPIO`, `include/nuttx/ioexpander/gpio.h`).
  `ioctl`s: `GPIOC_READ`, `GPIOC_WRITE`, `GPIOC_PINTYPE`, `GPIOC_SETPINTYPE`, `GPIOC_SETDEBOUNCE`,
  `GPIOC_REGISTER` (signal on interrupt), `GPIOC_IRQ_SETMASK`. Pin types: float / pull-up / pull-down input,
  push-pull / open-drain output, and interrupt pins (high, low, rising, falling, both, with wakeup variants).
  The device node also supports `poll()`, which is how a program waits for an edge.
- **Who creates the nodes:** the board, in C. `boards/arm/rp2040/waveshare-rp2040-zero/src/rp2040_gpio.c` has
  fixed arrays: `g_gpiooutputs[] = { 25 }`, one input (GPIO6), one interrupt input (GPIO11), counts in `board.h`
  (`BOARD_NGPIOOUT 3`...). The pin numbers are example values, they do not match the Zero's real wiring, and
  **`CONFIG_DEV_GPIO` is off in vaporOS's RP2040 build.** No Kconfig option picks pins.
- **Gap 1: declarative pins.** A user-wired device needs "these pins are outputs/inputs, named so" in the board
  descriptor, not C. Plan: a small vaporOS board-common helper (a patch or an out-of-tree file) that registers
  `/dev/gpioN` from a list generated by `vconfig`, e.g. `gpio.led_status = 16 out`. The same list becomes the
  runtime **device manifest** (name -> pin -> direction) so programs and vpm can see it.
- **Gap 2: the on-board LED of the Waveshare RP2040-Zero is a WS2812** (NuttX's `ws2812` defconfig puts it on
  GPIO16), not a plain LED, so it needs the PIO-based WS2812 driver (`CONFIG_RP2040_BOARD_HAS_WS2812`), not
  `/dev/gpioN`. Plain LEDs on spare pins are the right first GPIO test.

## Buses (all pin-configurable in Kconfig on the RP2040: good for descriptors)

- **SPI:** `CONFIG_RP2040_SPI0/1` with `..._RX_GPIO`, `_CS_GPIO`, `_SCK_GPIO`, `_TX_GPIO` options; userspace node
  via the common board `rp2040_spidev.c`. **I2C:** `RP2040_I2C0/1` likewise, node via `rp2040_i2cdev.c`.
  **PWM:** `RP2040_PWM` (+ `rp2040_pwmdev.c`). **I2S, ADC** similar.
- The common RP2040 board code already contains ready-made device glue: SD card over SPI (`rp2040_spisd.c`),
  displays (`ssd1306`, `st7735`, `st7789`, `gc9a01`), sensors (`bmp180/280`, `tmp112`, `ina219`, `max6675`),
  Ethernet (`enc28j60`, `w5500`). Each is a Kconfig switch plus board-level pin choices: these are the
  "presets for standardized hardware" the capability layer can wrap (an SD-card breakout = one descriptor).
- vaporOS already has `hardware/storage/sdcard-spi.conf` with pin parameters: that pattern generalizes.

## Simulator

- `SIM_GPIOCHIP` bridges to the host's real Linux gpiochip (`sim_gpiochip.c`), useless on a PC without GPIO
  hardware. **Gap 3: no virtual pins.** To test capability code on the sim we need a fake chip (a RAM ioexpander
  behind `/dev/gpioN`, readable and settable from a test). Without it only the board can test GPIO code.

## Proposed order (to be agreed)

1. Wire 2-3 LEDs and one button to free pins; user states which (the descriptor needs real numbers).
2. Descriptor syntax for named pins + the registration helper + `DEV_GPIO` on for the RP2040; blink test.
3. `vapor.gpio` in vlua over `/dev/gpioN` (`open("led.status")`, `write`, `read`, `wait_edge`), using the names
   from the manifest, never pin numbers.
4. Device manifest file + `requires` in `vpm.lua` + compatibility check in vpm.
5. Virtual pins on the sim, so steps 3-4 are testable without a board.
