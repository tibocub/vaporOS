# vaporOS on the Waveshare RP2040-Zero

Boots straight into vaporshell on a USB CDC-ACM serial console (`vinit`, no NSH).

## Workflow (from `vaporOS/`)

The board is described by `boards/rp2040-zero/` (see boards/README.md); the
commands are the same as for every other target, with `BOARD=rp2040`:

    make -f dev.mk build BOARD=rp2040   # compile  -> ../nuttx/nuttx.uf2
    make -f dev.mk flash BOARD=rp2040   # `reboot 1` into BOOTSEL, copy the UF2
    make -f dev.mk term  BOARD=rp2040   # vaporshell over USB (picocom; Ctrl-A Ctrl-X quits)
    make -f dev.mk run   BOARD=rp2040   # flash + terminal
    make -f dev.mk show  BOARD=rp2040   # every option of the image and why it is set

(`make -f dev.mk rp2040` builds, flashes and opens the console in one go.)

Press Enter if the prompt doesn't show: `vinit` waits for three Enters
(sent automatically by `term`). The first flash of a fresh board, or one
that is hung, needs BOOT held while plugging in; after that `flash`
needs no button presses. If the board crashes, the watchdog resets it and the
crash record can be read with `xd 2003ff00 96` (see
`patches/nuttx/rp2040-crashdump-waveshare.patch`).

## Reflashing without touching the board (humans and AI agents)

`make -f dev.mk flash BOARD=rp2040` (or `bash tools/rp2040-flash.sh [file.uf2]`, `run` = flash + console) puts a
**running** board into BOOTSEL by itself and copies the UF2; nobody needs to hold BOOT or replug. It tries, in order:

1. **1200 baud touch** (`stty -F /dev/ttyACM0 1200`): the CDC-ACM driver reboots into the ROM boot loader when the host
   sets the line rate to exactly 1200 bps (`patches/nuttx/cdcacm-reset-on-1200bps.patch`, `CONFIG_CDCACM_RESET_ON_1200BPS`,
   enabled by the `console/usb-cdcacm` descriptor). It runs in the USB interrupt, so it works **whatever the board is
   doing**: a program that owns the console, a hung task. Verified on the RP2040-Zero with `vui_textarea` running.
2. Fallback for firmware without the patch: Ctrl-C twice (programs treat it as quit), then `reboot 1` in the shell
   (`board_reset(1)` = ROM `reset_usb_boot`).
3. If the board is already in BOOTSEL (drive `RPI-RP2` present) it just copies.

Only a board that is not running this firmware at all, or whose USB stack is dead (no `/dev/ttyACM0`), needs BOOT held
while plugging in. After flashing the console takes ~7 s to reappear; `vinit` wants three Enters (`term` sends them).

To drive the board from a script (tests, benchmarks): open `/dev/ttyACM0` raw, send `\r\r\r`, then commands; see
`tools/rp2040-term.py` and `tools/rp2040-try.sh`. A program that draws a UI sends `ESC[6n` (cursor position request) once at
start to learn the screen size, so a scripted terminal must answer it (a pyte `Screen` subclass whose
`write_process_input` writes back to the port does). Read while you write: a writer that does not drain the board's
output can stall both sides.

## What is on the board

- `vinit` boots straight into `vaporshell` on the USB console (no NSH); a host
  that disconnects and reconnects gets a fresh shell.
- Tab completion (commands and paths), history, Ctrl-C / Ctrl-D.
- `vi`, `lua` and `vlua` (with a REPL: `vlua`, Ctrl-D to leave), toybox applets.
- NSH-style `free`, `df`, `mount`, `umount`, `ps`, `top`, `uptime`, `dmesg`, `xd`.
- `/flash`: 1 MB LittleFS that survives reflashing (`df` shows the space).
- ~55 KB of the 264 KB RAM used at idle, ~560 KB of the 2 MB flash.

Everything above is the same software as the simulator (`BOARD=sim-nsh`); only the
console, storage and watchdog differ, and those are the `[hardware]` lines of the
board file. Try a change on the simulator first, it needs no hardware.

## One-time host setup

- Toolchain in `~/toolchains`: `arm-gnu/` (Arm GNU 13.x `arm-none-eabi`),
  `picotool/`, `pico-sdk/` (needed for boot2). Override with `ARM_TOOLCHAIN_BIN`,
  `PICOTOOL_DIR`, `PICO_SDK_PATH`.
- Serial permission (the board is `0525:a4a7`):

      echo 'SUBSYSTEM=="tty", ATTRS{idVendor}=="0525", ATTRS{idProduct}=="a4a7", MODE="0666"' \
        | sudo tee /etc/udev/rules.d/99-nuttx-cdc.rules
      sudo udevadm control --reload && sudo udevadm trigger

- `picocom` for the terminal.

## Caveats

- Very fast bulk input is untested since the USB console fixes (it used to wedge it);
  paste in moderate pieces.
- `date` has no RTC to read: the clock starts at 2021-02-09 on every boot until set.
- Needs the patches in `patches/nuttx/` applied to `../nuttx` (`tools/apply-patches.sh`;
  see `patches/UPSTREAM.md` for what each one does and why).

## Where the RAM goes (measured 2026-10-27)

`free` on a fresh boot: **54.3 KB used** of 242 KB. Task stacks come out of this same heap
(`ps` shows `vaporshell` 16 KB, `vinit` 2 KB, plus 8 KB for every `tbx` command that is running), so
readings depend on how you measure:

- **Each pipeline stage costs about 10 KB while it runs** (one 8 KB `tbx` stack plus bookkeeping):
  `free` shows 61 KB, `free | grep Umem` 71 KB, `free | cat | grep Umem` 82 KB. It is not retained: the next
  plain `free` is back at the baseline. Measure with a plain `free`.
- **The first `localtime()`/`mktime()`/`os.date()` in any program allocates libc's time-zone table and keeps it
  after the program exits.** With the NuttX defaults (370 transitions x 20 types) that was 5.1 KB; this board has
  no zoneinfo files, so `LIBC_TZ_MAX_TIMES=16` / `LIBC_TZ_MAX_TYPES=4` in `board.conf` cut it to 1.6 KB. Time zones
  other than UTC would need these raised again.
- Not a cost (checked): `mkdir`, `cd`, `ls`, repeated `vlua` runs, 40 files open at once, lfs operations.
  Running a Lua script does not leak any more (the `os.exit` fix) once the one-time time-zone allocation is made.
